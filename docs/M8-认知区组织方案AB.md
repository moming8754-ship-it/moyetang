# 认知区「类似文件夹」的两个方案：A 与 B 的详细区别

> 起因：用户 2026-09-21 的反馈第 4 条 ——「认知区太乱了，我认为认知区应该搞一个类似文件夹的功能」。
> 三档方案里 **C（标签 + 全文搜索）用户已否掉**，剩下 A / B 在犹豫。这份文档就是为这次拍板写的。
> 结论在最后「怎么选」一节。

---

## 一句话区别

- **A = 给笔记贴一个"分组名"，列表按名字分段折叠**（像手机相册的"相簿"）。
- **B = 真的建文件夹，文件夹能装文件夹，笔记能拖进去**（像电脑上的目录树）。

---

## 一、数据怎么存

| | 方案 A | 方案 B |
|---|---|---|
| 新字段 | `Note.group: String`（空 = 未分组） | `Note.folderId: Option<String>` |
| 新文件 | 无 | **`folders.json`**：`[{ id, name, parentId }]` |
| 备份/导入 | 不用改（分组名跟着笔记走） | **必须把 `folders.json` 加进 `store/backup.rs` 的 `ENTRIES`** —— 漏了的话导入备份后文件夹结构全丢（笔记还在，但都成了"未分组"） |
| 切数据目录 | 不用改 | 要跟着带 |
| 旧数据兼容 | `#[serde(default)]` 一加就行 | 同样，但 `folders.json` 缺失时要能当"全在根下"处理 |

**A 的存储几乎没有额外负担；B 多一份文件、多一处"必须记得同步"的地方。**

---

## 二、界面上长什么样

### A：分组 + 折叠

```
▾ 密码学 (2)              ← 点标题折叠/展开
     基础密码学的学习规划
     密码学联系
▸ 随手记 (1)
▸ 未分组 (3)
     …
```

- 每篇笔记卡片上多一个入口（`▾` 或右键）：「移到分组 →」列出已有分组 + 「新建分组…」+ 「移出分组」。
- 分组的顺序：第一版**按名字排**（或按建立时间），不让你拖。

### B：真文件夹树

```
📁 课程
   📁 密码学
        讲义 1
        讲义 2
   📁 英语
📁 随手记
   各种各样（笑）
（根下散着的笔记）
```

- 文件夹可展开/收起、可改名、可删、可新建子文件夹。
- **笔记可以拖进文件夹，文件夹也可以拖进文件夹**（真指针拖拽，带落点高亮）。
- 右键/菜单：新建、改名、删除、在这里新建笔记。

**观感差别很大**：A 是"平铺 + 分段"，B 是真的树。笔记一多（50+），B 的层级会明显更清楚；
笔记少（十几篇以内），A 反而更清爽——树会让人为了"放哪儿"纠结。

## 三、各自能做 / 不能做

| 能力 | A | B |
|---|---|---|
| 按主题分组 | ✅ | ✅ |
| 一键折叠、眼前清爽 | ✅ | ✅（折叠文件夹） |
| **分组里再嵌套分组** | ❌ 不行 | ✅ 任意层 |
| **拖拽整理** | ❌ 不拖（只能用菜单"移到分组"） | ✅ 拖笔记/拖文件夹 |
| 文件夹排序、改名 | 改名 ✅（首次可只做改名） | ✅ |
| 文件夹颜色/图标 | ❌（以后可加） | 可加 |
| 同一篇笔记属于多处 | ❌ 一个分组 | ❌ 一个父文件夹（要"多处"得用标签 C 方案） |
| 100+ 篇笔记时还好用吗 | 一般（分组太长得靠折叠） | ✅ 好 |
| 搜索结果的表现 | 平铺（本来就没层级） | **要定规则**：我建议**平铺**、不带缩进（否则结果被结构切碎） |

---

## 四、要额外想清楚的规则（B 特有）

这些是"不写清楚就会变成 bug"的地方，A 一个都不需要：

1. **删文件夹时里面的笔记怎么办** → 我建议**挪到"未分组"，绝不跟着删**（和"删笔记只进回收站"一个调子）。
2. **不能把文件夹拖进自己的子孙里**（否则树会成环、渲染直接死循环）。
3. **同名文件夹**允许吗 → 建议允许（id 才是身份），但界面上加序号区分。
4. **空文件夹**要不要留着 → 留着（用户可能先建好框架）。
5. **树状图笔记和文本笔记**都能进文件夹 → 都能，不区分。

## 五、工作量与风险

| | 方案 A | 方案 B |
|---|---|---|
| 后端 | `Note` 加字段 + 一条 `note_set_group` 命令（操作式，只改这一处） | `folders.json` 读写 + 4~5 条命令（建/改名/删/移动）+ 拖拽落盘 |
| 前端 | 左栏按分组聚合渲染 + 折叠状态 + 一个"移到分组"菜单 | 左栏改成树（递归渲染）+ **自己写拖拽**（`elementFromPoint`、位移阈值、落点高亮）+ 菜单 |
| 验收 | 1 个脚本：建分组/移动/折叠/重开后还在 | 要**真实鼠标拖拽**验收（`-Action mouse`），和 M4 树拖拽一个量级；还要测"拖进自己子孙被拒""删文件夹不删笔记" |
| 预计 | **半天到一天** | **2~3 天**（含验收） |
| 风险 | 低（不碰笔记内容、不碰现有列表逻辑） | 中（拖拽 + 嵌套边界 + 备份要跟着改） |

## 六、先做 A 会不会"白做"

**不会。** A 存的是"分组名"，B 需要的是 `folderId`；从 A 到 B 就是
**把分组名映射成同名文件夹、给每篇笔记写 `folderId`** —— 一次性迁移，几十行代码，
而且数据不用重录。所以"先 A"不是套牢，是分两步走。

---

## 七、怎么选

**选 A**，如果你：
- 现在笔记不多（十几篇），痛点是"列表里混着东西看不清"；
- 想**今天/明天就用上**，不想为组织方式纠结；
- 以后真觉得不够，再升 B（迁移很便宜）。

**选 B**，如果你：
- 心里已经有一个"课程 / 主题 / 子主题"的层级结构，笔记会持续变多（几十上百篇）；
- 觉得"要靠菜单去移动笔记"不如"直接拖"来得顺手；
- 能接受这一轮多花 2~3 天，并且知道**拖拽要配真实鼠标验收**（这类东西用合成事件验会假绿，M4 栽过一次）。

**我的建议：A。** 理由：你现在只有 2 篇笔记，B 的层级优势还体现不出来，而成本差 2~3 倍；
A 做完立刻能用，且 A 的数据 B 能直接接管。

## 八、实际做的（2026-09-21 用户拍板选 A，当天做完）

**用户原话："方案先选A，我用几次再给你反馈。"** 这一版就是按上面那份清单做的，差别只有三处：

1. **折叠状态没放进 `store/ui.ts`，就放在页面自己的 `useState` 里。** 理由：折叠是"我现在想少看点"，
   不是设置项；页面切走再回来恢复全展开，是最不容易让人以为笔记丢了的做法（真写进 config 的话，
   "上次折叠着、这次打开也折叠着"会很像 bug）。
2. **顺序规则定死了：有名字的分组按名字的 Unicode 码点排**（稳定、不随中文拼音库变化），
   **未分组永远排最后**（那是"还没想好放哪儿"的收容所，不该夹在中间）。想让顺序听自己的就给名字加序号（`01 密码学`）。
3. **两个贴心处**（都是想过实际使用才加的）：
   ① 往一个**折叠着的**分组里移动笔记时，**那一组自动展开** —— 不然用户会以为笔记不见了；
   ② **搜索时平铺**（不按分组缩进）—— 搜东西时脑子里是"哪一篇"，结构只会把结果切碎。

**验收**：`tools/m8/run.ps1` **17 条全过**（老文件兼容 / 用界面菜单建组与移动 / 按分段渲染 / 未分组在最后 /
折叠与展开 / 搜索平铺 / 移进折叠组自动展开 / **直接翻磁盘文件核对 `"group"` 字段** / 收尾只删自己的测试笔记）。

**没做（属于方案 B）**：嵌套分组、把笔记拖进分组、分组排序/颜色。
用户说"我用几次再给你反馈" —— 要不要上 B，等他反馈。
